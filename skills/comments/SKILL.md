# Comments

註解只解釋「為什麼」，不解釋「做了什麼」。複述程式碼的註解刪掉。註解若在描述一條限制，優先把限制寫進程式本身，做得到就刪掉註解。

## 範圍

只處理這次改動涉及的註解，不清整個專案。使用呼叫者給的檔案或 diff。沒有的話，用工作目錄裡尚未 commit 的改動；沒有未 commit 的改動，就取最近一個 commit。

## 步驟

1. **派審查。** 啟動 `Agent`，`subagent_type: "Explore"`，模型依入口檔的「模型」一節，角色 `judgment`。交辦寫明：範圍、不改任何檔案、只回報。交辦直接帶入下方「判斷標準」。回報要列出動過的檔案、建議刪除的數量、每個 `MUST KILL` 一行（點名確切的符號），以及略過的項目。
2. **自己判斷每一項發現。** 對照 diff 逐項檢查，不照單全收。駁回：應用程式碼的改動、超出範圍、屬於例外的刪除、誤述的 `MUST KILL` 理由、把刻意保留的程式碼當成有問題的標記。
   - 保留要有證據：只有證明該註解是關於我們無法改變的東西，保留才成立。
   - 接受單薄的 `IMPORTANT` 或 `do not remove` 的刪除或保留之前，先追蹤它點名的符號，或讀 `${CLAUDE_PLUGIN_ROOT}/skills/why/SKILL.md` 並照做。
   - 刪除有歧義就不還原。保留被駁倒或仍有歧義就刪掉。
   - 只有拿得出確切的例外與限定範圍的證明，才還原刪除。
   - 補查審查漏掉的、限定範圍的 lint 與 TypeScript 抑制。涉及正確性或安全性的抑制仍是要處理的 `MUST KILL`。
   - 審查報告被駁回就還原，點名失敗原因，重派一次。第二份仍被駁回，就回報為未解決。
3. **刪除註解。** 你依採納的建議刪除註解。
4. **修正採納的標記。** 瑣碎的直接修：刪死路徑、移除參數、改用真正的 API。需要設計形狀的，先對整組標記與周圍程式碼畫出草圖，停在草圖，再往下實作。
5. **在範圍內做最小的根本原因修正。** 移除每一個被點名的 workaround。根本原因在範圍之外，就合併範圍內最小的修正，其餘回報為未解決。不擴大範圍，不修範圍之外的案例，不加治標的防護。
6. **處理限制註解。** 註解寫著 `do not remove`、`do not change wording`、`talk to X before changing` 時，若限制來自我們無法改變的東西，原樣保留。其餘提出範圍內成本最低的型別、執行期檢查、測試或 lint，把限制寫進程式。互動時等使用者核准。無人值守時需要呼叫者事先核准。核准就先編碼再刪註解。沒核准就刪註解，把該限制回報為未解決，並草擬範圍外的工作。

## 判斷標準

這些原樣寫進交辦。

可以留的註解只有：

- 法律或授權標頭。
- 外部依賴、平台、廠商或協定所強加、我們無法改變的不明顯行為。我們自己程式碼裡的意外不算，要刪掉註解，並把確切的符號標上 `MUST KILL`，要求改名、抽出、加型別或調整結構，讓行為不靠文字就看得懂。
- `// prettier-ignore`。lint 抑制只有在規則有缺陷、吹毛求疵或純屬風格時才能留。
- 定義公開 API 契約的文件註解。
- 解釋程式碼無法表達之限制的 issue 或 RFC 連結。

不確定某個註解是否適用上面的例外，就刪。

其餘都刪：旁白、橫幅、被註解掉的程式碼、為權宜之計辯護的說明。

- `eslint-disable`、`@ts-ignore`、`@ts-expect-error` 與類似的抑制：查那條規則。能抓到真正的 bug，或保護正確性或安全性，就刪掉抑制，並把有問題的符號標上 `MUST KILL`。
- `IMPORTANT`、`do not remove`、`too risky`、`fine for now` 和冗長的辯解只是警訊，不是定論。判定前讀附近的程式碼。說法在那裡看不出來，就追蹤它點名的符號或呼叫，或讀 `${CLAUDE_PLUGIN_ROOT}/skills/why/SKILL.md` 並照做。只有今天、在實際執行的路徑上證明為真，而且來自外部的限制才能留。我們自己程式碼的意外，連同 `MUST KILL` 一起處理。查過仍有疑慮就刪。
- 沒有證明屬於上述例外的冗長辯解，視為承認有問題。刪掉，不要改寫成更短的藉口，並標上 `MUST KILL`。
- 每個標記都要指向範圍內的程式碼，並屬實，不捏造。審查者只動註解與找出重構目標，不寫應用程式的程式碼。

## 回報

寫出：刪除數量、還原的註解、重派次數、設計草圖、修正、編碼方案、已編碼項目、未強制執行的限制，以及其他未解決的工作。
