# Correct

使用者一直為同樣的錯誤糾正這個專案裡的代理。修改專案，讓下一個代理不可能再犯。每次使用者糾正時重複這件事。

假設每個貢獻者都是代理：只看得到自己開過的檔案、照抄最近的範例、走最短的能編譯的路。把專案設計成：從單一檔案看起來正確的改動，對整個專案也正確。

## 找出錯誤類別

讀近期的 commit 紀錄、被撤回的改動、對話紀錄（`~/.claude/projects/<slug>/` 底下目前工作區的 `.jsonl`，`<slug>` 是工作區路徑把每個非英數字元換成 `-`，不要對其他專案 glob）、代理指示檔，以及解釋權宜做法的註解。把錯誤分組成類別。同一類發生過兩次才算數。

## 每個類別，在可行的最高層級修正

優先順序：架構、型別與 lint、測試、最後才是文件。

1. **用架構消除它。** 給每份 state 一個擁有者，給每件工作一種受支援的做法。隱藏內部實作，讓錯誤的 import 失敗。用單一事實來源取代手動同步的清單。刪掉代理會照抄的舊做法與死碼。
2. **用型別與 lint 強制。** 讓錯誤的狀態寫不出來。錯誤的程式碼仍能編譯時，加 lint 或檢查，錯誤訊息要指出該改用的檔案、型別或函式。模式已很普遍時，只在改動新增更多時才判失敗。
3. **測行為。** 修正或刪除任何「檢查的行為壞了仍通過」或「只有內部實作改變就失敗」的測試。
4. **最後才寫文件或代理規則，而且只用於需要判斷的情況。** 代理跳過它們時，不會有任何東西失敗。

## 修正並證明

現在就修最常見的類別，每個類別一個 commit。每個檢查都要證明它擋得住一次真實發生過的錯誤：把那次錯誤重現，確認新檢查失敗。用同一個可重複執行的指令跑檢查。例外寫在出問題的那一行，附上原因、到期日，以及使用者的核准。

## 維護規則表

在代理指示檔維護一張表，每條規則配上強制執行它的東西。使用者糾正時，修正錯誤並加上規則。規則已在表裡卻沒有東西強制執行，就是重犯，同一個改動裡用最高層級修正。錯誤不可能再發生時，刪掉那條規則。

**回報：** 每個類別及其證據、選的層級、為什麼更高的層級行不通。
