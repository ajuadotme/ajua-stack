# Blast radius

交付前，找出一個改動會在別處弄壞什麼。用於「X 的影響範圍」、「這可能弄壞什麼」，或審視一個還不信任的小 diff。

`/ajua-stack:how` 說明程式做什麼，`/ajua-stack:why` 說明它為什麼長這樣，本技能說明它會在別處弄壞什麼。列出呼叫端不是重點，grep 一秒就能做到。重點是 grep 看不到的破壞。

## 不信任自己的書面報告

聽起來合理的影響範圍報告沒有價值，對錯都一樣好讀。不要只交報告。找出整件事所仰賴的一兩個事實，用執行程式碼證明。

每個事實，依下列階梯盡量往上推到成本划算為止，並寫明停在哪一級：

1. 你說了算。單獨看沒有價值。
2. 你指出那一行：真實的 `file:line`，或所用 library 的原始碼。
3. 你證明壞的情況不可能發生：逐步走過失敗路徑，走不到。
4. 你執行過：一支呼叫真實程式碼的腳本或測試，你錯了就會大聲失敗。
5. 你在執行中的應用程式裡重現過。

第 4 級通常是一支小腳本，匯入應用程式實際交付的同一個 library，呼叫你擔心的那個函式。

## 步驟

1. **讀改動。** diff、新增、變更與刪除的符號，以及它現在做的不同的事，包括 diff 沒明講的部分。也看相關的 commit 訊息。
2. **找出那一個安全事實。** 多數看似有風險的改動，安全靠單一事實，例如「這個呼叫只丟掉已失效的快取項目，其他什麼都不做」。它成立，大多數風險就一次排除。時間花在這裡，不要花在一長串「也許」。
3. **看 grep 停下來的地方。** 讀所呼叫 library 的原始碼，檢查釘住的版本與本地 patch。弄清楚事情何時執行：microtask、unmount 與 teardown、不同框架的差別。追蹤符號搜尋漏掉的東西：API 回傳的 JSON、資料庫欄位、wire format、另一種語言讀同樣的位元組、feature flag、下游三跳之外的程式碼。
4. **對每個風險誠實。** 給真實的發生機率與發生時的真實代價。確認過的風險留下，檢查後排除的另列。引用真實的 `file:line`。搜尋找不到東西本身也是答案。絕不編造呼叫端或 API。
5. **證明那一個事實。** 寫腳本或測試執行真實程式碼，跑它，貼出結果。
6. **大型或範圍廣的改動。** 用 `panel` 角色派多個子代理各自回答同一個問題，合併答案。不同子代理會抓到不同的真實 bug。

## 回報

- **它做了什麼。** 變了什麼，包括不明顯的部分。
- **安全事實。** 陳述它，說明推到哪一級，展示證明。無法證明就寫「未證明」。
- **風險。** 每項寫如何壞掉、`file:line`、可能性與嚴重程度、如何檢查。重要的附上證明。
- **已排除。** 檢查過什麼，為什麼沒問題。
- **合併前。** 能抓到真實 bug 的最便宜測試或重現，包括你寫的那支腳本。

引用真實程式碼。內容若會被放到使用者以外的地方，先剝除私密資訊。
