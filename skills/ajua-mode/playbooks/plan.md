# 多階段計畫

把大工程拆成階段，寫成計畫檔。計畫檔就是交付物：只產出計畫檔，使用者明確同意後才執行。

1. **判斷要不要計畫。** 只改一兩個檔案、做法又明顯時，跳過計畫，說明原因，改走對應的流程表。
2. **先解決未定的問題。** 動筆前依 `prototype.md` 試做。只有試做無法決定的產品或偏好判斷，才問使用者。
3. **寫計畫檔。** 寫到 `docs/plans/<slug>.md`，使用者指定位置時照指定。開頭寫明要改什麼、依執行順序排列的階段、相依關係（哪些彼此獨立、哪些要等哪些），以及每個階段可以動哪些檔案。接著每個階段一節，附勾選框：依賴什麼、編輯的檔案、建立的那一個改動、會看到的結果、驗證方式。一個階段就是一個附有自己證據的改動，依入口檔原則「小步驗證」，驗證通過後各自 commit，再做下一個階段。
4. **每個階段都要有檢查，只有測試不夠。** 三種勾選框都勾上，階段才算驗證完成：unit；live，用具體情境與通過判定操作真正的介面；perf，寫明指標、量法、動工前先量好的基準，以及算失敗的數字；不影響效能的階段寫「不適用」與原因。改變互動方式的階段，完成後先給使用者審查，通過才做下一個階段。
5. **交回計畫後停止。** 回報計畫檔路徑。使用者明確同意後才開始執行。

**回報：** 計畫檔路徑、各階段與相依關係、需要使用者審查的階段、哪些還沒證明。
