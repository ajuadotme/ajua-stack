# 效能調校

每個修正都要對應到一筆量測。不用讀原始碼取代量測。

1. **擷取基準。** 在問題發生的同一個地方操作，擷取一份基準追蹤紀錄。基準與之後的每個數字都要通過第 2 步。
2. **檢驗數字。** 量之前，用要交付的措辭寫下預期的主張，讀量測腳本並記下它計時、計數、忽略什麼，查系統負載與核心數。機器忙又停不掉干擾時，兩邊交錯執行，並在回報說明。每題都用執行得來的證據回答：
   - **為什麼不是兩倍：** 在不回報的那次執行做 profile，點名限制因素並對應到原始碼，確認負載產生器沒有先飽和。變更沒讓數字動，先找出限制因素，再斷定變更沒用。
   - **有調校嗎：** 兩邊都用正式環境的跑法：release 建置、正式的旗標與環境變數、相同冷暖的快取、相同版本與資料。有一邊沒調校，先調校再量；無法調校就不從這次選贏家，使用者正在選擇要採用哪個做法時，縮窄主張也不算解決。
   - **有沒有突破極限：** 拿頻寬、核心數、被改那一塊的耗時佔比做算術。移除佔執行 10% 的部分，最多只快約 11%。超過極限代表量到快取、空操作或 bug。
   - **有出錯嗎：** 計算失敗數與非成功回應數，檢查輸出正確，不只是存在。腳本沒計數就加上。
   - **能重現嗎：** 每邊至少跑 5 次，A、B 交替，回報中位數與範圍。差距小於執行間的變異，就是沒有可量測的差異。結果接近時用 rank-sum 檢定或 harness 自己的統計。
   - **重要嗎：** 微觀結果旁邊，附上真實資料量與並行度下使用者等待的端對端量測，並報成整體佔比。只佔請求 1% 的函式，最多只讓請求快 1%。
   - **真的發生了嗎：** 確認工作在計時區間內執行，且結果有被使用。沒人迭代的 generator、沒人 await 的 promise、逾時，都會替沒發生的工作產生數字。

   使用者要求快速粗估時跑一次即可，仍要檢查「有出錯嗎」與「真的發生了嗎」，並說明只跑一次。在多個選項之間做選擇不算粗估。主張有差異卻點不出限制因素、有一邊沒調校，或無法檢查「有出錯嗎」「真的發生了嗎」時，結論定為無定論，並點名缺口。
3. **依口訣排假設。** 追蹤程式碼，讓假設有所依據。沒實際跑過，不宣稱已到效能上限。從最便宜的開始：不要做（結果沒人用的工作直接停掉，不只是變便宜）、要做但不重複做、少做一點、晚點再做、趁沒人在看時做、並行地做、用更便宜的方式做。前面的口訣已達目標就停。
4. **規劃並交辦修正。** 依追蹤紀錄規劃。修正跨越函式邊界時，先寫出改動後各函式的責任與介面。實作交給子代理，角色 `build`，模型依入口檔的「模型」一節。審查 diff，擷取修正後的追蹤紀錄。每次嘗試驗證過才試下一個。
5. **比較產出物。** 解析並比較，例如 JSON 轉進 sqlite、diff。「無法判定」或量錯地方都不算通過，要明確標出。
6. **存檔。** 依入口檔的「存檔」一節。

要針對某個指標持續改善，而不是一次性修正，改走 `hillclimb.md`。

**回報：** 結論（更快、更慢、沒有可量測的差異、無定論）、基準與修正後數字（附單位、次數、範圍）、差值、限制因素、產出物路徑。
