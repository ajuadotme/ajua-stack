# 搞懂

不改任何檔案。產出一份有出處的說明，或一個建議。

1. **實際去讀。** 追蹤問題涉及的程式或內容，不憑印象回答。問原因時，查版本紀錄裡當初的改動與說明（`git log`）。紀錄沒寫的，就說沒寫。
2. **寫出說明。** 依序：概觀、關鍵概念、運作方式、檔案位置、容易踩的坑。若是在選項之間做決定，改成給建議，附取捨比較表。
3. **標明出處。** 每個說法附檔名與行號。沒有出處的，標明是推論。

發現需要改東西時，停下來交回使用者，由使用者決定是否接著走 `fix-bug.md` 或 `feature.md`。

**回報：** 上述說明。被問「確定嗎」時給出真實判斷與理由。問題的前提有錯，直說。
