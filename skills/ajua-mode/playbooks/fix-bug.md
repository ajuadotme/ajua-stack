# 修問題

每一行改動都要對得上執行時的證據。「可能有幫助」的改動是假設，不是修正，不留下。證據推翻某個假設，就把它帶來的改動退回。

1. **自己重現。** 在問題發生的地方做：網頁就操作網頁，指令工具就執行指令，函式庫就寫一段程式呼叫它。不請使用者重現，除非你說得出碰不到那個地方的具體原因。重現不出來，就縮小條件、製造觸發情境，或加上紀錄輸出。記下重現的指令與輸出。
2. **找出原因。** 列出可能的原因。每一輪挑能排除最多可能性的檢查，取得執行時的證據，淘汰不成立的。狀態不清楚時加紀錄輸出並讀它，不猜。動手修之前，剩下的原因要有執行時的證據證實。
3. **規劃修正。** 只改證據支持的最小範圍。同樣的毛病別處也有，一起修。範圍大或代價高時交給子代理（角色 `build`），交辦寫明目標、檔案、完成條件。
4. **在同一個地方驗證。** 先移除找原因時加的紀錄輸出，再重跑第 1 步的重現，應該通過。結果不明確，或在別的地方驗的，不算通過，在回報裡標出。單元測試只證明那條分支，不證明問題消失。
5. **存檔。** 有低成本的本機測試路徑時，分成兩個 commit：先是會失敗的測試，再是修正。否則只 commit 修正。

**回報：** 壞了什麼、原因、怎麼修、怎麼驗證。原樣貼出修正前失敗、修正後通過的輸出。
