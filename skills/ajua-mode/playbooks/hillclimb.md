# 指標爬升

針對一個可量測的指標，朝目標反覆改進。一次性修正走 `fix-bug.md` 或 `perf.md`。核心紀律：一個改動、一次量測、保留或還原。不堆疊未測試的改動，不憑讀程式碼宣稱改善。

1. **先摸清工作負載，再定指標。** 追蹤目標，列出影響結果的實際工作負載維度（資料量、歷史、狀態、並行），挑一個能重現使用者抱怨的案例。沒有案例能重現，先修好重現，不爬升。定下指標、哪個方向算更好，以及可檢查的停止判定式。判定式要把目標與最少嘗試次數綁在一起，例如「比基準至少好 50%，且至少 10 輪」，讓早期的僥倖不能提早結束。使用者給了數字就用，否則跟使用者議定。
2. **建 harness，證明靈敏度，再凍結。** 跑幾組對比鮮明的實際工作負載，確認目標案例重現症狀、較輕的案例如預期區分開來。分不出來就改工作負載或指標。凍結前用 `perf.md` 第 2 步檢驗 harness，並讓它印出錯誤數與完成的工作量。凍結後由一個可重跑的指令輸出指標，取樣次數要壓過雜訊（N 次的中位數，不是單次）。改動前記錄基準指標，以及回歸關卡（必須持續通過的測試）的一次綠燈執行。
3. **開實驗紀錄。** 用一份 `experiments.tsv`，每次嘗試一列，欄位依序為 `id`、`hypothesis`、`change`、`before`、`after`、`delta`、`tests`、`verdict`（`kept` 或 `reverted`）、`note`。每次嘗試前先讀它。不進版本紀錄，加進 gitignore。
4. **假設要點出機制。** 以第 1 步摸清的架構為根據，寫出具體機制，例如「把 X 移出開機路徑，因為它擋住首次繪製」，不寫「試著 memoize 某個東西」。效能指標依 `perf.md` 第 3 步的口訣排順序，只借順序，不借那一步的停止規則。
5. **迴圈，每輪一個假設。**
   - 以嚴格的範圍把改動交給子代理，角色 `build`，模型依入口檔的「模型」一節。你監督並審查 diff，不自己動手寫。有多個獨立假設可同時試時，平行派給子代理，各用一個 worktree，依入口檔的「存檔」一節。
   - 用凍結的 harness 量改動前後，並跑回歸關卡。
   - 指標變動超過雜訊，且關卡維持綠燈，才接受。否則完整還原自己的改動，不用 `git reset --hard`。「可能有幫助」的微調不留。
   - 每個接受的修正一個 commit，只 stage 改過的檔案（`git add <files>`，不用 `-A`）。不論 `kept` 或 `reverted`，都記下那一列。
   - 每輪以一次檢查收尾，才開始下一輪。無人看管時，只從 `autonomous-run.md` 借喚醒機制，不借它的停止規則。
6. **突破第一個停滯期。** 連續多次被否決時，換類別、組合差一點成功的嘗試、重讀原始碼，或試更激進的做法，之後才下結論說爬完了。正確性與簡潔性比數字重要：還原會破壞行為的改善，保留能維持數字的簡化。
7. **停止。** 判定式成立，或剩下的點子效益小於成本時停。不放寬判定式來達成它。還有便宜、沒試過的假設時不放棄。卡住就提出來，不原地打轉。

**回報：** 指標與目標、基準到最終的數值與百分比差距、輪數（保留與還原各幾次）、每個接受的修正各一行、`experiments.tsv` 路徑、要繼續推進時下一個最佳點子。
