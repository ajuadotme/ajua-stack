# 常見錯誤

每條都是一個容易犯的錯，以及該怎麼做。

## 指令與成本

- **小改動也用 `ajua-mode`。** 它會派子代理做實作與驗證，風險高或要比稿時還會用到 `arena`、`swarm`、`interrogate`，花費更高。改個文字、調個顏色，直接說即可。
- **指令裡列出流程表或技能順序。** 手寫的順序容易漏掉流程表本來會做的步驟。只寫目標與限制。
- **完成條件模糊。** 「做得更好」沒有東西能檢查。寫能通過或失敗的結果。
- **一開頭就說你對原因的猜測。** Claude 會往你指的地方找。先說症狀，讓它自己找。

## 驗證

- **只看到「能編譯」就收工。** 編譯只證明語法沒問題。要看實際執行的結果、截圖或輸出。
- **相信沒檢驗的數字。** 快取是熱的，或有些工作沒計入，都會做出假的加速。要求說明數字受什麼限制，附上次數與波動。
- **全盤接受 `interrogate` 的結論。** 讀它捨棄的數量與原因，覺得捨棄過頭，就要它針對那一類再查。

## 版本紀錄

- **沒有 git 就開工。** 改壞了無法復原。專案沒有 git 時，`ajua-mode` 會停下來問，同意建立版本紀錄再繼續。
- **以為它會 push。** 外掛只在本機 commit，不 push，不開 PR。要推送請明說。
- **多個子代理共用同一份檔案。** 會互相覆蓋。同時改檔案時，各自用獨立的 worktree，`arena` 與 `swarm` 會自動這樣做。

## 設計

- **採用第一個做法。** 沒有前例的決定，先用試做比較。花得起時用 `arena`。
- **為一份沒試做過的抽象計畫反覆爭論。** 先試做回答問題，再檢查做出來的東西。

## 長時間工作

- **四個前提沒成立就放手。** 只會更快做出沒檢查過的東西。先確認第 5 章的四點，否則在旁邊看著跑。
- **用時間當完成條件。** 「跑四小時」不是條件。給能通過或失敗的判斷。

## 技能與回覆

- **同一個錯誤一直口頭糾正。** 只對這次有效。用 `/ajua-stack:correct` 把它變成檢查。
- **隨手改 `SKILL.md`。** 改壞的技能會影響之後每次執行。用「撰寫技能」流程表。
- **看不懂回覆就硬讀。** 用 `/ajua-stack:bro` 改成白話。
- **回來不知道做到哪。** 用 `/ajua-stack:catch-up` 看進度與等你決定的事。
