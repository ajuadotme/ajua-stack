# 動手前先搞懂

改看不懂的程式碼，容易修到症狀而漏掉原因。這章的指令多半只讀不改，讓你在動手前先看清楚。例外是 `blast-radius`，它會寫並執行一支驗證腳本。

## 弄清楚原因：直接描述

原因不明時，要的是調查結果，不是修正。說「先不要改檔案」，`ajua-mode` 會選「搞懂」流程表：

```
/ajua-stack:ajua-mode 調查為什麼背景同步每隔幾小時就逾時。列出已知的事、你看了哪些資料、最可能的原因。先不要改任何檔案。
```

調查結果指向修正時，把修正當成新任務。

## how：現在怎麼運作

```
/ajua-stack:how 通知是怎麼去重的？
```

`how` 讀程式碼，說明這個部分的執行流程、關鍵資料結構與不明顯的地方。問你真正想知道的問題，答案會更準。

## why：為什麼這樣做

```
/ajua-stack:why 重試上限為什麼設成五次？
```

`why` 從版本紀錄查：引入這段程式的 commit、之後每次修改的原因。它會區分紀錄寫了什麼與它自己的推論。紀錄沒寫的，它會說沒寫。

## teach：講到你懂為止

```
/ajua-stack:teach 教我這次修改怎麼改變重試的行為，並說服我它修的是原因而不是症狀。
```

`teach` 自己讀程式，問原因時查版本紀錄，範圍大時派 `Explore` 子代理，然後一步步講解。也能用在 Claude 自己的選擇：

```
/ajua-stack:teach 教我為什麼你選擇用快取而不是每次重新查詢。
```

## recall：找回以前的脈絡

```
/ajua-stack:recall 上週做的匯出功能
```

`recall` 從過去的對話紀錄與版本紀錄（commit、被 revert 的修正、未併回的 branch）重建某個主題的來龍去脈：做到哪、決定了什麼、下一步是什麼。在舊主題上開新工作前先用。

## blast-radius：改了會影響哪裡

```
/ajua-stack:blast-radius 目前工作目錄裡把 formatDate 回傳格式改成物件的那個改動。
```

`blast-radius` 在改動做完、交付前，查它會在別處弄壞什麼，並執行程式證明最關鍵的安全事實。範圍大時，派多個子代理各自回答同一個問題再合併。

## 看不懂回覆：bro

回覆技術上完整，但你還是不懂時：

```
/ajua-stack:bro
```

它把上一則回覆改成白話，更短，不用行話。

## 回來接續：catch-up

離開一陣子，或讓 Claude 在長對話裡自己跑時：

```
/ajua-stack:catch-up
```

它說明你上一則訊息之後發生的事，並列出等你決定的事，各附建議與風險。只讀不改。

接續中斷的工作則是描述任務即可，`ajua-mode` 會選「接手工作」。見第 5 章。
